**Motivo:** no se pudo confirmar contra qué rama base se abrió el PR real (los comandos `gh pr view`/`gh pr list` requieren red y no están disponibles en este entorno de ejecución), así que se aplicó la corrección que resuelve el síntoma reportado bajo cualquiera de las dos causas plausibles (base distinta de `main`, o ausencia de trigger por `push` a una rama feature) sin debilitar la protección de `main`.

Se completaron varios detalles que el checklist no cubría literalmente, siempre a favor de lo ya definido:
1. **Filtro de "Tipo" resuelto en el cliente, no como segundo parámetro de backend.** El Paso 1 pide explícitamente un ÚNICO parámetro de texto libre; agregar un segundo parámetro estructurado (`tipoComercio` exacto) para el selector de tipo de la UI hubiera sido alcance no pedido. Se pide al backend hasta 50 candidatos (`TOPE_CANDIDATOS`, el tope máximo ya validado por `ListarComerciosCercanosQuerySchema`) filtrados por `q` si corresponde, y el filtro de tipo + la paginación de 10 en 10 se resuelven en el cliente sobre ese conjunto — dado el volumen de `comercios` de este proyecto (single-tenant, 12 registros en `docs/SEED.md`), es la opción más simple sin perder corrección (Sección 7).
2. **Sincronización mapa/listado por construcción, no por un mecanismo de sincronización explícito.** El AC pide que ambas vistas "se actualicen de forma sincronizada" — se logró que la tabla y `MapaComercios` reciban literalmente el mismo array `items` (ya filtrado/paginado) como única fuente de datos, en vez de mantener dos estados independientes que haya que sincronizar manualmente: es la forma más simple de garantizar la propiedad pedida, no una casualidad de la implementación.
3. **Debounce de 300ms para el texto de búsqueda.** El ticket no lo pide explícitamente, pero sin él cada tecla dispararía una request nueva — se agregó por ser una práctica estándar de UX/rendimiento para búsquedas de texto libre, consistente con no golpear la API en cada `keystroke`.
4. **Página nueva en `docs/SITEMAP.md` (`/comercios`), consulta pública sin login** — mismo criterio que `/reportes`/`/municipio/eventos`: no se agregó a `RUTAS_PAGINA_PROTEGIDAS` en `middleware.ts` porque el endpoint que consume (`GET /api/comercios/cercanos`) ya es de lectura pública desde la actividad anterior.

Verificación manual en navegador (Chrome vía preview local): la página `/comercios` renderiza correctamente el buscador, el selector de tipo y el layout tabla+mapa; la llamada real a `GET /api/comercios/cercanos` falla en este entorno de desarrollo por dos limitaciones del entorno ajenas a este ticket — (a) no hay una base de datos real conectada (sin `DATABASE_URL` de Supabase en este sandbox) y (b) el logger `pino` de este proyecto revienta con "the worker has exited" al intentar loguear ese error en modo `next dev` en esta máquina Windows — el mismo fallo ocurriría hoy en CUALQUIER endpoint de este proyecto que dependa de Prisma en este entorno puntual, no es un defecto de `ListarComerciosCercanos` ni de `BuscadorComercios.tsx` (la suite de tests, que sí corre contra fakes/mocks sin depender de una base real, pasa 100%).
**Motivo:** un caso de uso/componente sin sus puertos/adaptador/endpoint (cuando aplica) no es invocable ni verificable con una request real — mismo razonamiento que todas las decisiones anteriores de este sprint. Resolver el filtro de tipo en el cliente evita construir un segundo parámetro de backend que el ticket no pidió, sin sacrificar corrección dado el volumen real de datos de este proyecto. Diseñar la sincronización mapa/listado como "una sola fuente de datos" en vez de un mecanismo de sincronización aparte es la solución más simple que satisface el AC literal, coherente con la Sección 7 del proyecto.
